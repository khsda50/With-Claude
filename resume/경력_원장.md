## 3. 경력 사실 원장 — IP DV 우선순위로 재배열

> 기존 이력서의 배열: `통합검증 → 설계·Sign-off → 검증인프라 → 방법론`
> **이번 배열: IP 단위 검증·VIP → 방법론 → Coverage/Regression → 설계 이해 → SoC 통합**
> 같은 사실이지만 JD 담당업무 1~4번 순서와 일치하게 뒤집었다.

### A. IP 단위 검증 환경 · VIP 개발 ★최우선

JD 담당업무 2번(In-house VIP 개발), 자격요건 1번에 직접 대응.

- **Ethernet GMAC UVM 레퍼런스 검증 환경 직접 구현** — 재사용 표준의 기준 환경이 됨
- **USB 2.0 IP 단위 시뮬레이션 환경 구성** (2022.06~09, Synopsys USB IP, 기여도 100%)
- **DPI 기반 전사 IP Unit 시뮬레이션 환경 구축** — 회사 전체 IP 단위 검증 인프라
- Bus connectivity 검증 환경 구축 및 **스코어보드 설계**
  - ※ 기존 이력서 표현은 "**상용** VIP 기반" — in-house VIP 개발직에서는 감점 요인.
    직접 설계한 스코어보드/환경 쪽으로 서술 무게를 옮길 것.

### B. UVM 검증 방법론 · 재사용 구조 ★최우선

JD 자격요건 3번(신규 Protocol/Custom IP UVM Agent 설계)의 간접 근거.

- **재사용 UVM 검증 환경 표준화 주도**
  - IP env·sequence의 **Top-level 수직 재사용 구조 설계**
  - 차세대 HPC 과제 **전 DV 인원에게 적용** (개인 산출물 → 조직 표준으로 확산)
- **Dynamic Test Loading (save/restore) 도입** → 시뮬레이션 TAT 절감
- 전사 AI Transformation Task Force **SoC 그룹 대표** 참여

### C. Coverage · Regression 인프라

JD 담당업무 4번(Coverage Closure)에 걸리는 블록이자 **이 지원서의 최대 약점.**

보유한 것:
- **Coverage DB 병합 플로우 구축** — closure 를 돌리기 위한 *인프라* 는 세웠다
- **Port toggle coverage** — 보유한 커버리지 지표는 이것뿐이다
- ATE용 **GLS 테스트벡터 추출**
- DPI 기반 Top/서브시스템 시뮬레이션 환경 구축·운영
  - **고객사와 공동 사용**
  - 칩 구조 변경에 따른 **Dual-die 환경 개편 리딩**

보유하지 않은 것 (2026-08-11 확인):
- **Coverage closure 경험 없음.** functional coverage 모델을 세우고 → 회귀를 돌려
  hole 을 분석하고 → directed test 로 메워 목표치에 도달시키는 사이클을 돌린 적이 없다.
- 따라서 커버리지 도달률·회귀 규모 같은 정량 지표도 존재하지 않는다.
  **없는 숫자를 만들어 쓸 수는 없다.**
- Port toggle coverage 는 연결성 확인용 지표다. JD 가 말하는 Code/Functional
  Coverage Closure 와 같은 층이 아니므로 같은 이름으로 포장하면 면접에서 바로 깨진다.

### D. RTL 설계 · Front-end Sign-off (검증 직무에서의 차별점)

- 8nm ADAS SoC **Lidar 서브시스템 RTL 설계** 및 Top 통합
- Ethernet GMAC·USB·Lidar IP **Front-end Sign-off** (Lint·CDC·LEC·Synthesis·STA)
- 내부 SoC Platform용 **CMN-700 설계 지원**
- **AxCACHE 성능 이슈**를 검증 중 발견 → **제어 SFR 추가로 해결** → 여러 서브시스템에 확대 적용
  - 이 항목이 원장 전체에서 가장 강한 서사: *발견 → 설계 변경으로 해결 → 수평 전개*.
    "검증만 하는 사람"이 아니라는 증거이므로 어느 칸에서든 살릴 것.

### E. SoC Top-level 통합 검증 (기존 주력 → 이번엔 보조)

- Ethernet GMAC·USB·Lidar 등 **다종 IP/서브시스템 Top 통합 검증**
- **CMN-700·FlexNoC** 인터커넥트 정합성·데이터패스 검증 및 이슈 해결
  - CHI/AXI 데이터패스, **SAM 라우팅 이슈 규명**
- **Mask ROM 부트로더** 등 시스템 부트 시나리오 검증 (C 기반)
- Main SoC 플랫폼(**Arm Cortex-A55**)·**C2C(SUE)** Top 통합 검증 담당 (진행 중)
- Chiplet die 간 연결 사양 분석

## 4. 진단 — 왜 기존 이력서가 IP DV에서 안 통했는가

3개 지원서 모두 동일한 구조적 문제를 공유한다.

1. **첫 화면이 전부 "Top 통합 검증"이었다.**
   읽는 사람에게 각인되는 정체성이 *SoC 통합 검증 엔지니어*였다.
   IP DV 자리에서는 "IP를 깊게 판 사람"이 아니라 "붙이는 사람"으로 읽힌다.

2. **가장 강한 IP DV 자산이 맨 아래 [방법론]에 묻혀 있었다.**
   `GMAC UVM 레퍼런스 환경 직접 구현`, `전사 IP Unit sim 환경`, `UVM 재사용 표준화`는
   이 JD가 요구하는 바로 그 능력인데 마지막 블록에 3줄로 눌려 있었다.

3. **USB 2.0 IP 단위 환경(기여도 100%)이 프로젝트 목록 9번에 숨어 있었다.**
   IP 단위 검증 환경을 혼자 세운 경험은 이 직무의 정면 근거인데 목록 항목으로만 존재했다.

4. **"상용 VIP 기반"이라는 표현.**
   In-house VIP 개발을 담당 업무로 명시한 조직에서는 역효과.

5. **Coverage closure 경험이 없다.**
   기존 이력서는 "Coverage DB 병합 플로우 구축"까지만 썼다. 이것은 사실이지만
   JD 담당업무 4번·자격요건 4번이 요구하는 것은 *플로우* 가 아니라 *closure* 다.
   보유 지표는 port toggle coverage 뿐이므로, 이 항목은 숫자가 빠진 문제가 아니라
   **경험 자체가 없는 갭**이다. 4개 담당업무 중 하나가 여기에 걸린다.

6. **직무 전환 논리가 없었다.**
   SoC DV → IP DV 이동에 대한 설명이 없어, 지원자가 왜 이 자리를 원하는지 근거가 비어 있었다.

## 5. JD 요구 ↔ 보유 근거 매핑

| JD 요구 | 보유 근거 | 상태 |
|---|---|---|
| SystemVerilog/UVM VIP·TB·Test Case 개발 | GMAC 레퍼런스 환경, USB IP 단위 환경, 전사 IP Unit 환경 | **충족** |
| Digital IP Spec 기반 검증 계획 수립 | Front-end Sign-off + RTL 설계 경험 (스펙 독해력) | 충족 |
| 신규 Protocol / Custom IP **UVM Agent 설계·구현** | 재사용 구조 설계 + `q_chan_vip` | **보강 중** |
| Code/Functional **Coverage Closure** | 병합 플로우 + port toggle coverage 뿐 | **갭** |
| (우대) Spec 기반 Custom UVM Agent **A-to-Z** | `q_chan_vip` | **보강 중** |
| (우대) HBM, DDR/LPDDR Memory 검증 | 없음 | **갭** |
| (우대) Full-Chip **Mixed-Level(Schematic & RTL)** 검증 | 없음 (순수 디지털) | **갭** |

### 갭 정리

셋 다 경력으로는 메울 수 없다. 세 번째가 가장 무겁다.

- **메모리(HBM/DRAM) 검증 경험 없음** — 우대사항. 프로토콜·전력 시퀀스 이해로 우회.
- **Mixed-Signal 검증 경험 없음** — 우대사항. 조직 소개 첫 줄이 Analog-Digital Mixed IP.
- **Coverage closure 경험 없음** — 이쪽은 우대사항이 아니라 **자격요건 4번이자 담당업무
  4번**이다. 위 둘보다 등급이 높은 갭이고, 보유 지표가 port toggle coverage 뿐이라
  경력 서술로 우회할 방법이 없다. 유일한 대응은 `q_chan_vip` 에서 functional coverage
  모델을 직접 세운 것을 근거로 쓰는 것이며, 그마저 **아직 회귀로 돌려 closure 를 본 것은
  아니다**(시뮬레이터 없음). 지원서에서 이 항목을 부풀리면 면접에서 가장 먼저 깨진다.

## 6. 갭 대응 자산 — `q_chan_vip`

`../q_chan_vip/` — Q-Channel(전력/클럭 핸드셰이크) **Custom UVM Agent를 스펙만 보고 A-to-Z로 구현**한 것.
JD 우대사항 1번을 정면으로 겨냥한 자산이며, 지원서의 **경험/특허** 칸에 넣을 후보.

현재 구현 범위 (약 1,640줄):

| 구성 | 파일 | 상태 |
|---|---|---|
| Interface | `qch_if.sv` | 구현 |
| Sequence item 계층 | `qch_items.sv` (base/controller/device_response/device_active) | 구현 |
| Config object | `qch_config.svh` | 구현 |
| Controller driver | `qch_controller_driver.svh` | 구현 |
| Device driver (responder) | `qch_device_driver.svh` | 구현 |
| Monitor | `qch_monitor.svh` | 구현 |
| Agent / Sequencer / Responder seq | `qch_agent.svh` 외 | 구현 |
| 테스트 | items unit / controller / monitor / loopback / coverage 5종 | 구현 |
| **Covergroup (functional coverage)** | `qch_coverage.svh` | **구현, 단 미실행** |

- 설계 근거 문서: `../q_chan_vip/docs/superpowers/specs/` (sequence_item, driver/monitor,
  coverage model 3종)
- 후보안 4종 비교·채택 근거까지 문서화되어 있음 → **"스펙 해석 → 설계 판단 → 구현"** 과정을 보일 수 있는 형태
- Q-Channel은 CRMU/PMU 전력 관리용 핸드셰이크 → **HBM base die의 전력 시퀀스 문맥과 연결됨**

### Coverage 갭 대응에서 이 자산이 할 수 있는 말과 못 하는 말

**할 수 있는 말** — functional coverage 모델을 스펙에서 직접 도출했다.
상태·전이·응답 지연·QACTIVE cross를 설계하고, 왜 transition bin 대신 `(prev,state)` 쌍으로
판정했는지, 왜 `illegal_bins`를 쓰지 않았는지까지 근거를 남겼다. **"커버리지 모델을 세울 수
있다"는 주장의 근거로는 충분하다.**

**못 하는 말** — closure. 이 환경에 SystemVerilog 시뮬레이터가 없어
(`vcs`/`xrun`/`vsim`/`verilator`/`iverilog` 전부 부재) **컴파일도 실행도 하지 않았다.**
회귀 → hole 분석 → directed test 추가 → 목표 도달 사이클은 돌리지 않았다.

- 무료 시뮬레이터로는 우회가 안 된다. Verilator·Icarus 는 SV covergroup 을 지원하지 않아
  functional coverage 자체를 못 돌린다. **상용 시뮬레이터 접근이 전제 조건이다.**
- 따라서 지원서에서는 "모델을 설계·구현했다" 까지만 쓰고, closure 를 했다고 쓰지 않는다.
- 면접에서 "돌려봤나" 는 거의 확실히 나오는 질문이다. "환경이 없어 미실행" 이라고
  정확히 답하는 편이, 돌렸다고 했다가 결과를 못 대는 것보다 낫다.

## 7. 확인·복원이 필요한 항목

지원서 작성 전에 채워야 하는 것들.

- [ ] 부서명 (폼 필수)
- [ ] 급여 (폼 필수, 만원)
- [ ] 재직중일 때 `근무종료년월` 입력 방식
- [ ] **TAT 절감 수치** — Dynamic Test Loading 도입 전후 (%, 시간)
- [ ] 재사용 UVM 표준을 적용한 **DV 인원 수 / 과제 수**
- [ ] 신규 IP 검증 환경 구축 기간 단축폭 (기존 → 개선)
- [ ] 전사 IP Unit 시뮬레이션 환경으로 검증한 **IP 개수**
- [ ] AxCACHE 이슈를 확대 적용한 **서브시스템 개수**
- [ ] Top 통합 검증에서 규명한 **이슈 건수**
- [ ] Port toggle coverage 를 적용한 범위 (IP 수 / 서브시스템 수) — 있는 지표는
      이것뿐이니 정확히 쓰는 편이 낫다

> 위 숫자들이 이번 지원서의 승부처다. 같은 사실을 숫자 없이 쓴 것이 3회 탈락한 이력서였다.

**Coverage 도달률·회귀 규모는 이 목록에서 뺐다.** 복원할 숫자가 아니라 애초에 없는
숫자다(2026-08-11 확인). 이 자리를 억지로 채우는 대신 §5 갭 정리의 방침을 따른다.
