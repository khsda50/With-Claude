- 공백 포함 **493자** → 여유 7자

**v7 에서 고친 것**

- `버스 connectivity 검증 환경 자동화 구성` →
  **`버스 스펙 config 기반 컴포넌트 자동 생성 구조에 스코어보드 설계`**.
  `자동화` 라는 뭉뚱그린 말 대신 **config-driven elaboration** 이라는 메커니즘을
  그대로 쓴다. 아는 사람만 쓸 수 있는 문장이 되고, 동시에 **본인 몫이 스코어보드
  쪽이라는 것도 정확해진다** (프레임워크 전체를 만든 것이 아니다)
- Q/P-Channel VIP 에 `(agent·커버리지 모델)` 추가. 최강 카드가 맨몸 한 줄이었다
- Lidar 표기를 `Lidar integration` / `Lidar RTL 설계` 로 줄여 중복감 완화

**Regression 은 쓰지 않는다**

회귀 환경이나 스크립트를 만든 것이 아니라 돌린 것뿐이므로 쓰지 않는다.
앞선 §8 평가에서 "회귀 흔적이 약하다" 고 적은 것은 **관찰이지 채우라는 뜻이 아니다.**
DTL 줄의 `회귀 구조·규칙 수립` 은 실제로 한 일이므로 그것으로 충분하다.

**VIP 두 항목을 합치지 않는 이유**

| | 합치면 |
|---|---|
| JD 대응 | 담당업무 2번이 `In-house VIP 개발` **및** `3rd Party VIP 도입/활용` 으로 둘을 따로 요구한다. 합치면 한쪽만 대응하는 것처럼 보인다 |
| 신호 강도 | `VIP 개발·확장` 으로 뭉개지며 **In-house 개발이라는 가장 강한 신호가 희석**된다 |
| 대비 | 두 줄이 나란히 있으면 "만들 줄도 알고 남의 구조를 읽을 줄도 안다" 는 대비가 생긴다. 합치면 사라진다 |

합쳐서 자리를 만드는 대신 **다른 항목에서 줄여 Q/P-Channel VIP 를 두껍게** 했다.
`DPI 기반 sim 환경` 과 `Lidar` 표기에서 덜어냈다.

## B. 자기소개서 1 — 지원동기 / 향후 계획 / 퇴사 동기  ★재작성 (2안)

### 관통선

> **"나에게 검증의 깊이는 만드는 데서 나온다."**

세 가지를 한 칸에 넣는 문항이라, 셋이 각각 다른 방향에서 같은 문장을 증명해야 한다.

| 블록 | 답하는 질문 | 관통선과의 관계 |
|---|---|---|
| 퇴사 동기 | 왜 **떠나나** | 깊이를 쌓고 싶은데 두 역할을 오갔다 |
| 지원 동기 | 왜 **여기인가** | 내 깊이는 만드는 데서 나오는데, 그게 상시인 조직 |
| 향후 계획 | **무엇이 될 것인가** | 만들어서 남기는 사람 |

- **퇴사동기와 지원동기는 같은 말을 하면 안 된다.** "깊게 하고 싶다"는 떠나는 이유로는
  완벽하지만 지원 이유로는 아무 회사에나 해당된다. 지원 이유는 **다른 회사로 치환되지
  않는 문장**(표준 VIP 없는 In-house IP가 많은 base die)이라야 한다.
- **HBM은 세대를 이어 가는 제품**이라는 점이 ①의 깊이와 ②를 잇는다. 회사 칭찬이 아니라
  *내 이유와 이 회사의 구조가 맞물린다*는 논증이라 안전하다.

### 넣지 않은 것

- 회사 칭찬("글로벌 리더", "기술력") — 지원동기 칸에서 가장 흔한 낭비
- 학벌·회사 규모 암시("부족하지만", "작은 조직에서") — 없던 프레임을 심는다
- Coverage를 **자산**으로 언급 — closure 경험이 없는 약점을 스스로 불러온다
- C(경력기술서)에 있는 사례의 **서술** — 이름만 스치고 지나간다
- "설계가 싫다"는 뉘앙스 — 담당업무의 `Lidar RTL 설계·IP FE Sign-off`와 충돌한다

### V1 — 태도([일하는 방식]) 포함  ·  994자

```text
[전 직장 퇴사 동기]
DV 팀에 속해 있지만 팀 운영상 설계를 겸해, Lidar RTL 설계와 IP FE Sign-off도
맡았습니다. 설계 경험은 RTL을 읽는 눈이 되었지만, 두 역할을 오가는
동안 검증에 쌓이는 깊이는 제한적이었습니다. 검증이 전업인 조직에서 담당 IP를 오래
맡고 싶어 이직을 결심했습니다.

[지원 동기]
제게 검증의 깊이는 만드는 데서 나왔습니다. 표준 VIP가 없는 프로토콜은 스펙만 보고
만들었고, 고객사의 SystemVerilog class 기반 AMBA VIP는 인수해 내부를 파악하고
확장했으며, 판정할 방법이 없는 IP에는 스코어보드를 세웠습니다. 프로토콜이 무엇을
보장하는지 끝까지 따져야 만들 수 있어, 환경을 만드는 일은 제게 검증을 가장 깊이
들여다보는 방법이었습니다.

HBM Digital Design(검증)은 담당 업무 네 가지 중 두 가지가 In-house VIP 개발과 UVM
검증 환경 구성입니다. 표준 VIP가 없는 In-house IP와 Mixed IP가 많은 base die에서는 스펙을 읽고 환경을
직접 설계하는 일이 상시로 필요하다고 이해했습니다. HBM은 세대를
이어 가는 제품이어서 한 IP를 오래 맡겠다는 제 이유도 성립합니다. 가장 오래 해온 일이
이곳에서는 곁일이 아니라 본업이라는 점이 지원 이유입니다.

[일하는 방식]
같은 일을 두 번 하게 되면 그 자리를 구조로 바꿔 왔습니다. 채널마다 따로 만들던
Q/P-Channel 환경은 재사용 가능한 VIP 하나로 모았고, 회귀마다 반복되던 부트 구간은
스냅샷 기반 규칙으로 걷어냈습니다. 환경부터 케이스, 스코어보드, RTL 설계까지 혼자
감당하는 조직에 있었기에 몸에 밴 방식입니다.

[향후 계획]
담당 IP의 검증 환경을 스펙 단계부터 맡아 커버리지로 닫고, 다음 세대가 다시 쓸
In-house VIP 자산을 남기고자 합니다. 3년 내에는 Mixed-Signal 검증까지 넓혀 회로
설계자와 같은 언어로 논의하는 검증 담당자가 되고자 합니다.
```

- 공백·줄바꿈 포함 **994자** / 1,000자 → 여유 6자 (**한 글자도 더 못 넣는다**)
- `[일하는 방식]`이 태도 블록이다. 형용사("성실", "책임감")를 한 개도 쓰지 않고
  **동사와 사실로만** 썼다. 고른 태도는 *"반복을 참지 않고 구조로 바꾼다"* —
  통과한 결과를 의심하는 태도는 C(Lidar/AxCACHE)가 이미 행동으로 보여주므로 제외했다.
- 마지막 문장(*환경부터 케이스, 스코어보드, RTL 설계까지 혼자 감당하는 조직*)이
  스펙 열세에 대한 실질적인 답이다. 대기업 4년차에게는 대개 없는 이력이라서다.
  단 "다 해봤다"로 읽히지 않게 **일하는 방식의 근거**로만 붙였다.


- 공백·줄바꿈 포함 **983자** / 1,000자 → 여유 17자
- V1의 `[일하는 방식]` 자리에 **두 번째 문단**이 들어갔다. *SoC 검증은 완성된 IP를 붙여
  놓고 그 사이를 보는 일이 큰 비중 → 그래서 IP 하나를 파고드는 깊이가 통합에 필요한
  만큼에서 멈췄다 → 붙여서 보는 쪽보다 만들어서 보는 쪽에 강점이 있다*.
- **3회 탈락에서 비어 있던 것이 이 논리다.** 지금까지 이력서는 전부 SoC DV였는데
  지원 직무는 IP DV이고, 그 사이를 잇는 문장이 어디에도 없었다.

### 어느 쪽인가

| | V1 | V2 |
|---|---|---|
| 채우는 구멍 | 사람됨·태도가 안 보인다 | SoC DV → IP DV 전환 논리가 없다 |
| 위험 | 태도 블록은 누구나 쓴다 | 사람 냄새가 적고 논리만 남는다 |
| 태도 | 명시 | C가 행동으로만 보여줌 |

- 태도는 **D(기타사항)에서도 쓸 수 있지만**, 전환 논리는 5-1 말고 들어갈 칸이 없다.
  그래서 **V2를 본안으로, 태도는 D로 넘기는 조합**을 권한다.
- 반대로 D를 입사 시기·거주지 같은 사무적 내용으로만 채울 생각이라면 V1이 맞다.

## C. 자기소개서 2 — 경력기술서 (987자)  ★주력

**목록이 아니라 서사로.** 담당업무 칸이 업무를 촘촘히 나열하므로, 여기서 같은 항목을
다시 훑으면 1,500자 중 상당수를 중복에 쓴다. C 는 A 가 구조상 못 하는 것 —
**왜 그렇게 했는가, 무엇이 문제였는가, 결과가 무엇인가** — 만 담는다.

```text
[검증할 수 있는 상태로 만드는 일]
담당 서브시스템에는 Q-Channel과 P-Channel이 여러 개 있어, 채널마다 환경을 따로
만들면 같은 일이 반복됩니다. 재사용 가능한 In-house UVM VIP 하나로 일원화하기로 하고
스펙만 보고 A-to-Z로 설계했습니다. 가장 오래 고민한 것은
sequence_item을 무엇으로 잡을지였습니다. 이 프로토콜은 상태 여섯 개와 신호 네 개만
정의할 뿐 트랜잭션을 명명하지 않아, 아이템을 정하는 일이 곧 설계였습니다. 후보 네
가지를 비교해 근거를 문서로 남겼고, 그 결정에서 커버리지 어휘가 도출되도록 구조를
잡았습니다. 아이템이 표현하지 못하는 현상은 검증이 볼 수 없기 때문입니다.

Ethernet GMAC은 반대였습니다. IP도 스펙도 있었지만 우리 설정대로 동작하는지 판정할
방법이 없었습니다. 전송 전 랜덤화한 설정값을 보관했다가 실제 TX/RX 패킷과 대조하는
스코어보드를 만들고, memory descriptor도 스펙에 맞춰 파싱했습니다. 없는 것이
무엇이냐에 따라 만들어야 할 것이 달랐습니다.

[통과한 테스트에서 이상을 찾다]
```

### 세 서사가 각각 다른 능력을 증명한다

| 서사 | 증명하는 것 |
|---|---|
| ① 검증할 수 있는 상태로 만드는 일 | **만든다** — Q/P-Channel VIP, GMAC 스코어보드 |
| ② 통과한 테스트에서 이상을 찾다 | **찾아낸다** (디버그) |
| ③ 검증 환경을 팀 표준으로 | **조직에 남긴다** |

### ①에 GMAC 을 합친 이유 — 앞선 판단을 뒤집는다

앞서 "GMAC 스코어보드는 VIP 와 같은 축이라 뺀다" 고 했는데, 그것은 **서사가 따로
있을 때** 의 이야기다. **한 서사 안에 두 사례를 넣으면 축이 겹치는 것이 아니라 같은
능력을 두 번 보인 것** 이 된다 — 반복이 아니라 보강이다.

그리고 합치니 더 나은 것이 나왔다. 두 사례가 **정반대** 다.

| | 있던 것 | 없던 것 | 만든 것 |
|---|---|---|---|
| Q-Channel | 스펙뿐 | 어휘(트랜잭션 정의) | seq_item 체계 |
| GMAC | IP · 스펙 | 판정 방법 | 스코어보드 · descriptor parser |

마지막 문장 `없는 것이 무엇이냐에 따라 만들어야 할 것이 달랐습니다` 가 둘을 묶는다.
사례 나열이 아니라 **판단 기준을 가진 사람**으로 읽힌다.

부수 효과로 구멍 하나가 메워졌다 — 직전 판까지 GMAC 스코어보드가 담당업무에만 있고
C 에는 없어서 **왜 만들었는지가 어디에도 없었다.**

### 각 서사에서 가장 중요한 한 줄

**①-1** `아이템이 표현하지 못하는 현상은 검증이 볼 수 없기 때문입니다.`
seq_item 설계를 왜 그렇게 고민했는지의 근거.

**①-2** `없는 것이 무엇이냐에 따라 만들어야 할 것이 달랐습니다.`
두 사례를 하나의 판단으로 묶는 문장.

**②** `판정은 통과였으므로 결과만 봤다면 넘어갔을 문제입니다.`
테스트가 통과했는데 이상을 느꼈다는 것 — pass/fail 만 보는 사람은 잡을 수 없다.

**③** `현재 진행 중인 HPC 과제에서 DV 팀의 UVM 표준 구조로 쓰이고 있습니다.`
인원수보다 "팀 표준" 이 낫다. 개인 산출물이 조직 자산이 됐다는 뜻이다.

### 규모에 대한 조정

`controller 와 device 양쪽 driver, monitor, agent, 커버리지 모델까지 구현했습니다`
문장을 뺐다. `~까지` 가 "이만큼이나 했다" 는 신호를 주는데, 신호 네 개짜리 프로토콜의
VIP 는 작은 것이 정상이다. **글이 크게 들렸다가 실물이 작아 보이는 낙차**를 만들 필요가
없다. 산출물 범위는 담당업무 칸의 `(agent·커버리지 모델)` 로 충분하다.

### 자기소개서 3(D)과의 분담

| 칸 | 담당하는 면 |
|---|---|
| 담당업무 | 사실 — 무엇을 만들었나 |

### 몰입·끈기를 넣은 방식

원하는 인상은 *열정 있고 엉덩이 무거운 사람*. **시간이 아니라 동기와 사실로** 쓴다.

| 넣은 문장 | 무엇을 증명하나 |
|---|---|
| `궁금한 것을 남겨 두면 잘 넘어가지 못해, 일과가 끝난 뒤에도 붙들고 있을 때가 많았습니다` | 인용의 뒷부분(기쁘지 아니한가)을 채운다. **원인이 궁금증**이라 근태가 아니라 몰입으로 읽힌다 |
| `당장 필요해서가 아니라 제가 맡은 IP라 알고 싶었고` | 시켜서가 아니라는 동기 |
| `업무 중에 다 보지 못한 것은 따로 시간을 내어 읽었습니다` | **자기 시간을 썼다** — 야근이 아니라 자기계발이라 근태 신호가 없다 |
| `과제로 주어진 일이 아니었습니다 / 손이 비는 때에 … 찾아보고 계획해` | 주도성. 형용사 없이 열정을 증명 |

**야근·시간 표현은 쓰지 않는다.** *시간 가는 줄 모르고* 는 상투구라 앞뒤 문장까지 같은
급으로 끌어내리고, 심사자에 따라 `효율이 낮다` / `관리 부담이 있다` 로도 읽힌다.
얻는 것(열심히 하는 사람)보다 잃는 것이 크다. **같은 재료를 서류에서는 동기로, 면접에서는
시간으로** 말하면 된다 — 면접은 사람이 맥락을 보므로 몰입으로 전달될 여지가 크다.

### 사실 정정

- **Q-Channel VIP 는 과제 기간 내 업무다.** 과제 밖에서 한 일로 쓰지 않는다
- **과제 일정 밖에서 한 것은 UVM 표준화와 DTL.** 손이 비는 때에 직접 찾아보고 계획해
  만들어 둔 것이므로, 세 번째 문단의 근거는 이 둘로 맞췄다
- 그래서 세 번째 문단에서 Q/P-Channel VIP 를 뺐다. C 첫 서사와 중복이기도 했다

### 그대로 지킨 선

- "팀장들이 좋아한다" 는 쓰지 않는다 — 검증 불가능한 문장은 신뢰를 깎는다
- IP 버그를 찾았다고 쓰지 않는다 — PHY RTL 모델 오동작이지 IP 결함이 아니다
- RTL 설계·Sign-off 는 넣지 않는다 — 디자인하우스라는 회사 형태 때문이지 자원한 일이
  아니므로 적극성의 근거가 되지 않는다

("IP 및 Mixed 설계 검증")에 대응하는 서술이 비어, 도구 만든 사람으로만 읽힌다.

**빠진 어휘** — JD가 쓰는 검증 단어가 칸에 거의 없다:

| JD 어휘 | 현재 |
|---|---|
| 검증 계획 수립 | 없음 |
| Test Case 개발 | 없음 |
| Regression Test | 없음 |
| 디버그 / 이슈 규명 | SAM 라우팅 1개 |

**새 블록 순서** (문장은 미작성):

```
[IP/서브시스템 검증]        ← 신설·최상단
- 다종 IP 검증계획 수립 → 테스트케이스 개발 → 회귀 운영
- 인터커넥트 데이터패스 검증, SAM 라우팅 이슈 규명
- 부트 시나리오 검증 (Mask ROM)
- AxCACHE 성능 이슈 발견·해결   ← C와 층위 분리해 짧게만

[검증 환경·VIP]             ← 기존 1블록을 2번째로
[방법론·인프라]             ← 축소
[RTL 설계·Sign-off]         ← 2줄 → 1줄
```

- 예산 확보: 설계·Sign-off와 방법론에서 줄여 검증 블록 자리를 만든다.
  검증 직무 지원서에서 설계 이력이 2줄까지 갈 필요는 없다.
- C(경력기술서) ①블록 제목도 `스펙 기반 IP 검증 환경 구축` →
  `IP 검증과 검증 환경 구축` 으로.

**Q-Channel 서술 주의**

사내 적용은 bind 연동 구조 구성 + 예제 시나리오 동작 확인까지 진행됨.
"검증 완료"로 쓰면 면접에서 커버리지·발견 이슈를 반드시 되묻는다. 권장 표현:

> 사내 검증 환경에 bind 연동 구조를 구성하고 예제 시나리오로 동작 확인

사실 그대로이고 세기도 크게 다르지 않다.

### I-2. 반영할 신규 정보 (2026-08-11 확인)

**Test case 개발 실적** — "검증한 티"를 만드는 핵심. 셋 다 고유명사가 있어 강하다.

| 대상 | 내용 | 상태 |
|---|---|---|
| Cortex-A55 CPU 클러스터 | DSU 기능 분석 → 스펙 지원 feature 기준 케이스 개발 | 진행 중 |
| Ethernet GMAC (DPI) | ECC·timestamp 등 기능 케이스 | 완료 |
| Lidar 서브시스템 (DPI) | integration 관점 검증 | 완료 |
| UVM 기반 GMAC 환경 | constrained-random + **스코어보드 + descriptor parser** | 완료 |

**GMAC 을 두 방법론으로 검증한 것이 이 표의 숨은 자산이다.** DPI 환경에서는
ECC·timestamp directed 케이스, UVM 환경에서는 constraint 기반 random. 한 줄에 같이
쓰면 "랜덤 좀 써봤다" 가 아니라 **directed 와 constrained-random 을 다 써봤고 어디에
무엇이 맞는지 안다** 로 읽힌다.

DSU 항목이 특히 세다. "클러스터 내부를 다 보진 않지만 DSU 기능을 파악해 자사 스펙이
지원하는 feature를 케이스로 만든다" 는 **스펙 기반 검증계획 수립**(JD 자격요건 2번)의
실물 증거다.

**VIP 프레이밍** — 사용자 제안 채택:

> SoC DV였지만 그 안에서 필요한 VIP를 직접 만들어 썼다

직무 전환 논리를 한 문장으로 해결한다. 과제 적용 여부를 항목마다 밝힐 필요는 없다.
**Q-Channel 방침 변경 (2026-08-11)**: 개인 과제로 두지 않고 **과제에 적용**한다.
규모가 작아 부담이 적다는 판단. 적용되면 담당업무 칸에 넣을 수 있고, C ①블록의
`개인 과제로` 는 사내 과제로 승격된다.

- 현재 진행 상태: bind 연동 구조 구성 + 예제 시나리오 동작 확인
- **제출 시점 기준으로 쓴다.** 적용이 끝나 있으면 `사내 CRMU 검증에 적용`,
  아직이면 `bind 연동 구성 및 동작 확인` — 후자도 충분히 강하다.
- GMAC·USB·AMBA VIP 만으로도 "필요한 VIP를 직접 만들어 썼다" 는 이미 성립하므로,
  Q-Channel 이 늦어도 프레임은 무너지지 않는다.

**IP 간 동작 검증 — 앞선 판단 수정**

SoC 통합을 "주변부" 로 밀라고 했던 것을 되돌린다. JD 조직 소개에
`Digital IP 및 Subsystem/Top Level 검증` 이 명시돼 있고, HBM base die 도 in-house IP 를
붙인 구조라 IP 간 연동 검증이 그대로 필요하다. 순서만 IP 먼저, Top 나중.

**새 블록 구성**

```
[IP·서브시스템 검증]                        ← 신설·최상단
- Cortex-A55 CPU 클러스터 검증: DSU 기능 분석 →
  스펙 지원 feature 기준 테스트케이스 개발 (진행 중)
- Ethernet GMAC: ECC·timestamp 기능 케이스(directed) +
  UVM 환경 constraint 기반 random 패턴 검증
- Lidar 서브시스템 integration 검증
- 인터커넥트 데이터패스·SAM 라우팅 이슈 규명, AxCACHE 성능 이슈 발견·해결

[검증 환경·VIP]
- SoC 검증에 필요한 VIP를 직접 제작 — GMAC UVM 환경, USB 2.0 IP 단위 환경
- SV class 기반 고객사 AMBA VIP 인수·구조 파악·확장
- DPI 기반 전사 IP Unit sim 환경 구축·운영

[방법론·인프라]                             ← 1~2줄로 축소
[RTL 설계·Sign-off]                        ← 1줄로 축소
```

예산: 새 블록이 들어가면 500자 초과. 설계·Sign-off 를 1줄로 줄이고 방법론에서
Coverage DB·GLS 를 덜어내야 맞는다. 실측은 다음 작업.

### I-3. 추가 확인 (2026-08-11) — 판정 축과 Q-Channel 의 진짜 동기

**① GMAC UVM 스코어보드 — 지금까지 지원서에 없던 최대 누락**

| 층 | 내용 |
|---|---|
| 랜덤화 | frame format(일반/jumbo), payload memory data pattern, 수반 data size |
| 예측 | 전송 전 랜덤화된 레지스터 설정값(frame type, length, pattern)을 버퍼에 저장 |
| 비교 | TX/RX 패킷 도착 시 기대값과 실제값 대조 |
| 파싱 | memory interface **descriptor parser** 를 IP 스펙에 맞게 구현 |

predictor + comparator 구조의 정식 스코어보드다. descriptor parser 는
**스펙을 읽고 스펙 준수 파서를 구현한 것** 이라 JD 자격요건 2번의 직접 증거.
`constrained-random 자극 → 스코어보드 판정 → 스펙 기반 파싱` 이 한 벌로 성립한다.

**담당업무 칸 반영 (필수)**

```
- Ethernet GMAC UVM 환경: frame format·payload 랜덤화, 설정값 대 실제 패킷 비교
  스코어보드 및 IP 스펙 기반 memory descriptor parser 구현
```

**② CPU 서브시스템도 UVM 기반이고, FW 기반 검증도 UVM TB 위에서 한다**

- Cortex-A55 클러스터 검증(DSU feature 케이스)이 UVM 환경에서 진행 중
- **FW 기반 검증을 UVM 테스트벤치에서 수행** ← HW/SW 경계를 다 다룬다는 신호.
  HBM base die 도 test firmware 로 구동하는 영역이 있어 문맥이 이어진다

**③ Q-Channel VIP 의 동기가 바뀐다 — 개인 공부가 아니라 과제 요구**

CPU 서브시스템 안에 **Q-Channel / P-Channel 이 다수** 존재해, 채널마다 따로 검증하는
대신 **일원화·재사용 가능한 In-house VIP** 를 만들어 대응하려는 것.

이 사실이 지원서 전체에서 가장 큰 변화다.

- 지금까지 서술: "직무 준비를 위해 개인적으로 만들어 본 agent"
- 실제: **"다수 채널을 재사용 가능한 하나의 VIP 로 일원화하려는 과제 대응"**
- JD 담당업무 2번(In-house VIP 개발)·자격요건 3번(신규 Protocol UVM Agent 설계)에
  정면으로 걸리고, **동기가 실무 문제 해결이라 설득력이 다르다**
- 만들어 둔 `qch_multi_env` / virtual sequencer 도 곧 "채널이 많다" 는 실제 요구에
  대한 답이 된다. 우연이 아니라 요구에서 나온 구조로 설명할 수 있다

→ C ①블록의 `개인 과제로` 를 삭제하고, 담당업무 칸에도 아래 형태로 넣는다.

```
- 서브시스템 내 다수 Q-Channel/P-Channel 검증을 일원화하기 위한
  In-house UVM VIP 개발 (스펙 기반 A-to-Z)
```

**④ 남은 확인 항목**

- [ ] 스코어보드가 실제로 잡은 버그 사례 (있으면 면접 최고 재료)
- [ ] DSU 에서 검증한 feature 목록, cluster power state 포함 여부
- [ ] FW 기반 검증에서 FW 를 직접 작성했는지
