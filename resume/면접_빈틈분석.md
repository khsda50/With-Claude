# 면접 빈틈 분석 — HBM DV 면접관 엔지니어 관점

전제: 면접관은 SK hynix HBM Digital Design(검증) 조직의 시니어 DV 엔지니어.
In-house VIP 를 만들고 UVM 환경을 세우고 커버리지로 닫는 일을 매일 하는 사람.
그 사람이 이 지원서를 읽고 무엇을 물을 것인가.

근거: `경력_원장.md`, `작성초안.md`, `../JD_HBM-Digital-Design-검증.md`

## 1. 판정 메커니즘이 없다 ★새로 발견, 가장 급함

지원서 전체를 훑으면 이런 말들이 있다 — 환경 구축, 테스트케이스 개발, Sign-off,
이슈 규명, 커버리지 DB 병합. 그런데 **"무엇으로 통과/실패를 판정했는가"** 가 한 줄도
없다.

DV 면접에서 이건 거의 반드시 나오는 질문이다. 검증 엔지니어를 가르는 지점이기 때문이다.

**예상 질문**
- "GMAC UVM 환경에서 pass/fail 은 무엇으로 판정했나? 스코어보드가 있었나?"
- "레퍼런스 모델을 썼나, 아니면 예상값을 테스트가 직접 들고 있었나?"
- "ECC 케이스는 어떻게 맞았는지 확인했나?"
- "DPI 환경에서는 C 쪽에서 self-check 했나?"

**지금 상태**: 알 수 없음. `q_chan_vip` 조차 스코어보드를 "사용 여부 미정" 으로
남겨 뒀다(spec 에 명시). 랜덤 패턴을 넣었다고 했는데 **랜덤은 판정이 자동화되어
있지 않으면 의미가 반감된다** — 면접관이 정확히 그 지점을 짚는다.

**해야 할 일**
- [ ] 실제로 무엇을 썼는지 정리: 스코어보드 / 레퍼런스 모델 / assertion /
      C 기반 self-check / 로그·파형 육안 확인 — 있는 그대로
- [ ] 하나라도 있으면 **담당업무 칸에 반드시 넣는다.** 지금 이 칸의 가장 큰 결손이다
- [ ] 없으면 답변 준비: "판정은 대부분 C 기반 self-check 와 assertion 이었고,
      트랜잭션 레벨 스코어보드는 다뤄본 적이 없다" 처럼 정확히

## 2. Coverage Closure

`경력_원장.md` §5 에 정리된 대로 **경험이 없다.** 보유 지표는 port toggle coverage 와
Coverage DB 병합 플로우(=closure 를 돌릴 인프라)뿐.

**예상 질문**
- "커버리지 몇 % 까지 닫아봤나?"
- "hole 은 어떻게 분석했나? directed 로 메웠나 constraint 를 고쳤나?"
- "회귀는 몇 개 테스트를 어떤 주기로 돌렸고, 실패 triage 는 어떻게 했나?"
- "functional coverage 모델은 누가 정의했나?"

**준비된 답의 뼈대** (부풀리지 않는다)
> 제가 한 것은 **closure 를 돌릴 인프라**입니다 — 서브시스템별로 흩어진 결과를 모으는
> Coverage DB 병합 플로우를 만들었고, IP 통합 구간은 port toggle 로 연결성을 봤습니다.
> 지표를 세워 hole 을 분석하고 메워 닫는 사이클은 담당해 본 적이 없습니다.
> 그래서 Q-Channel VIP 에서 커버리지 모델을 직접 설계해 봤습니다 — 상태·전이·응답
> 지연·QACTIVE cross 로 잡았고, transition bin 대신 아이템에 직전 상태를 실어
> 리셋 경계 오판정을 피하는 식으로 판단했습니다.

없는 것을 없다고 말한 뒤 **바로 옆에 한 것을 붙이는** 구조. 이게 최선이다.

## 3. HBM / DRAM 도메인 지식 ★공부로 해결되는 유일한 항목

우대사항이지만 **면접에서는 반드시 나온다.** 모르고 가면 "직무 이해 없이 지원했다"
로 읽힌다. 반대로 준비하면 우대사항 하나를 부분적으로 덮는다.

최소 준비 범위:
- HBM 스택 구조 — base die + core die, TSV, microbump
- **base die 가 하는 일** ← 지원 직무의 대상. PHY, TSV 인터페이스, 테스트 로직,
  전력 관리, (HBM3E 이후) 로직 확장
- channel / pseudo-channel 구조, bank group
- DRAM 기본 동작 — ACT / RD / WR / PRE / REF, tRCD·tRP·tRAS 같은 타이밍 파라미터의 의미
- refresh 와 전력 상태 (self-refresh, power-down) ← **Q-Channel 과 직접 연결된다**
- HBM2E / HBM3 / HBM3E 세대별 대역폭·핀수 대략

**연결 포인트**: refresh·power-down 은 전력 시퀀스이고, 지원자가 만든 Q-Channel
agent 가 다루는 것이 정확히 전력 핸드셰이크다. **"HBM 을 몰라도 전력 시퀀스는 안다"**
로 이을 수 있는 유일한 다리다. 이 연결을 미리 준비할 것.

## 4. Mixed-Signal

조직 소개 첫 줄이 `Analog-Digital Mixed IP`. 경험 없음.

**예상 질문**
- "AMS 시뮬레이션 돌려본 적 있나?"
- "아날로그 IP 를 디지털 회귀에 어떻게 넣을 건가?"

**최소 준비**: RNM(Real Number Modeling) / wreal 개념. 아날로그를 실수 신호로
모델링해 디지털 시뮬레이터에서 함께 돌리는 방식. "SPICE 를 돌리는 게 아니라
동작 모델로 바꿔 회귀에 태운다" 는 그림만 정확히 알아도 대화가 된다.

정직한 답 + 방향 제시: "해본 적 없다. 다만 RNM 으로 모델을 만들어 디지털 회귀에
포함시키는 접근으로 이해하고 있고, 입사 후 최우선 학습 과제로 두고 있다."

## 5. CPU 클러스터 검증의 깊이

현재 진행 중인 일이라 **가장 깊게 파고들 항목**이다. 본인이 "클러스터 내부를 다
들여다보지는 않는다" 고 했으므로, 면접관은 정확히 그 경계를 물을 것이다.

**예상 질문**
- "DSU 에서 구체적으로 어떤 feature 를 검증했나?"
- "cache coherency 는 봤나? snoop 트랜잭션은?"
- "cluster power state 전환은? (이게 Q-Channel 과 이어진다)"
- "MPAM, ECC, RAS 는?"

**해야 할 일**
- [ ] 실제로 케이스를 만든 feature 목록을 **정확히** 적어둘 것
- [ ] 안 본 것은 안 봤다고. CPU 검증 경험자 앞에서 아는 척은 즉시 드러난다
- [ ] **cluster power state 를 봤다면 최우선으로 준비.** Q-Channel·CRMU 와 직접
      연결되어 이 지원서 전체를 하나로 묶는 고리가 된다

## 6. 6월 재지원 ★기회로 쓸 것

같은 회사에 6월 지원 후 탈락, 재지원이다. **"6월에도 지원하셨네요. 그때와 달라진
점이 뭔가요?"** 는 나올 가능성이 높다.

이건 위기가 아니라 **준비된 답이 있으면 가장 강한 카드**다. 대부분의 지원자는
"더 열심히 준비했다" 로 답하고 아무것도 증명하지 못한다.

**답의 뼈대**
> 6월에는 제 경력을 SoC 통합 검증 중심으로 썼습니다. 떨어지고 나서 JD 를 다시 읽었는데,
> 이 직무가 두 번 강조하는 게 **신규 프로토콜에 대해 스펙만 보고 UVM Agent 를 만드는
> 능력**이더군요. 제가 해온 일 중 그것에 해당하는 게 무엇인지 다시 정리했고, 부족하다고
> 느낀 부분은 직접 만들어 봤습니다 — Q-Channel agent 입니다.

*떨어진 이유를 스스로 분석하고 행동으로 옮긴 사람* 이 된다. 실제로 그렇게 했으므로
지어낸 이야기도 아니다.

## 7. 그 밖에 나올 질문

**재사용 UVM 표준화 — 최고 카드이므로 깊게 준비**
- "수직 재사용 구조가 구체적으로 어떤 모양인가? IP env 를 top 에서 어떻게 재사용했나?"
- "sequence layering 은? virtual sequencer 를 썼나?"
- "다른 팀원들이 실제로 썼나? 저항은 없었나? 어떻게 설득했나?"
- → **화이트보드에 그림으로 설명할 수 있어야 한다.** 말로만 하면 흐려진다

**Q-Channel VIP — 코드를 볼 수 있다**
- 공개 저장소이므로 면접관이 실제로 열어볼 수 있다. SVA 미구현, 스코어보드 미정이
  다 보인다
- → **먼저 말하는 게 낫다.** "체커는 SVA 로 분리하기로 설계했고 아직 미구현입니다"
  는 설계 의도가 있는 미완이라 오히려 괜찮다. 들켜서 설명하면 변명이 된다
- "왜 sequence_item 을 그렇게 나눴나" 는 문서가 있으니 강점

**AxCACHE 이슈 — 가장 강한 서사이므로 반드시 깊게**
- "어떻게 발견했나? 어떤 증상이었나? 왜 AxCACHE 라고 특정했나?"
- "SFR 추가는 누가 결정했나? 설계자를 어떻게 설득했나?"
- → 발견 경위·디버그 과정·설득 과정 셋 다 준비

**커리어 방향**
- "SoC DV 에서 IP DV 로 좁히는 건데, 다시 넓은 걸 하고 싶어지지 않겠나?"
- "디자인하우스에서 대기업으로 옮기는 문화 차이는?"
